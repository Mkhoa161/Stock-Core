## Summary

Phase 3 has three independent work streams: (1) a new TypeScript script `generateTickers.ts` that scrapes Wikipedia and writes a committed `tickers.json`; (2) rewiring `generateStaticParams` in the Next.js `[ticker]/page.tsx` to read from that JSON file instead of the live API; and (3) Terraform for the S3 + CloudFront frontend delivery layer.

**Critical verified finding:** With `trailingSlash: true` (current `next.config.ts`), Next.js emits `out/companies/index.html` and `out/company/AAPL/index.html` (not `.html` files). A CloudFront distribution backed by a private S3 bucket (OAC, website hosting disabled) does NOT automatically resolve `companies/` to `companies/index.html` — only the root `default_root_object = "index.html"` works. Without a URI rewrite, every route except `/` serves the 404 page. A **CloudFront Function** (viewer-request) rewriting requests to append `index.html` is required. This is an addition to D-09's component list.

**Important:** The existing welcome page (`frontend/src/app/page.tsx`) contains `<a href="/companies">` — a bare anchor without a trailing slash. CloudFront would request S3 key `companies` (no slash, no extension), receive a 403, and serve the 404 page. The CloudFront Function must handle BOTH trailing-slash paths (`/companies/` → `/companies/index.html`) AND bare extensionless paths (`/companies` → `/companies/index.html`).

**Second critical verified finding:** `app/not-found.tsx` in Next.js 15.4.1 with `trailingSlash: true` produces BOTH `out/404.html` AND `out/404/index.html`. `out/404.html` contains the custom content. D-09's CloudFront error configuration referencing `/404.html` is correct.

**Primary recommendation:** Add `aws_cloudfront_function` (viewer-request URI rewrite for both trailing-slash and bare extensionless paths) and `aws_s3_bucket_ownership_controls` (BucketOwnerEnforced, required for OAC) to the Terraform configuration alongside the resources specified in D-09.

### Pattern 1: generateStaticParams Reading Local JSON

**What:** Read committed JSON at build time using Node.js `fs` + `path.join(process.cwd(), ...)`.

**When to use:** Static export where dynamic data cannot call a live API during build.

**Why `process.cwd()` not `__dirname`:** `next build` runs with cwd at the `frontend/` workspace root. `process.cwd()` resolves to `frontend/`, so `src/data/tickers.json` is the correct relative path. `__dirname` would resolve to the Next.js internal build path, which is unreliable.

```typescript
// Source: [VERIFIED: local build test on Next.js 15.4.1]
// frontend/src/app/company/[ticker]/page.tsx
import { readFileSync } from 'fs';
import path from 'path';

export const dynamicParams = false;

export function generateStaticParams() {
  const filePath = path.join(process.cwd(), 'src/data/tickers.json');
  const raw = readFileSync(filePath, 'utf-8');
  const data = JSON.parse(raw) as { tickers: string[] };
  return data.tickers.map((ticker) => ({ ticker }));
}
```

**Note:** `frontend/tsconfig.json` has `"resolveJsonModule": true`, so `import tickers from "@/data/tickers.json"` would work as an alternative. D-05 locks `fs.readFileSync`, so the pattern above is authoritative.

### Pattern 2: generateTickers.ts Script

**What:** Standalone TypeScript script using axios + cheerio to scrape Wikipedia's S&P 500 table. Writes output cross-package using `path.resolve(__dirname, ...)`.

**Key constraint:** The script is invoked with cwd at `backend/`. Writing to `frontend/src/data/tickers.json` requires resolving relative to `__dirname` (the compiled script location), not `process.cwd()`.

```typescript
// Source: [ASSUMED] — pattern based on scrapeSP500.ts conventions + path resolution rules
// backend/src/scripts/generateTickers.ts
import axios from 'axios';
import * as cheerio from 'cheerio';
import * as fs from 'fs';
import * as path from 'path';

const WIKIPEDIA_URL = 'https://en.wikipedia.org/wiki/List_of_S%26P_500_companies';
// __dirname at runtime = backend/dist/scripts/ (ts-node: backend/src/scripts/)
// Resolve to repo root first, then to frontend data dir
const OUTPUT_PATH = path.resolve(__dirname, '../../../frontend/src/data/tickers.json');

async function generateTickers(): Promise<void> {
  console.log('🔍 Scraping S&P 500 tickers from Wikipedia...');
  const response = await axios.get(WIKIPEDIA_URL, {
    headers: { 'User-Agent': 'StockCore/1.0 (personal project)' },
  });
  const $ = cheerio.load(response.data);
  const tickers: string[] = [];

  $('table.wikitable').first().find('tbody tr').each((_i, el) => {
    const cols = $(el).find('td');
    if (cols.length >= 2) {
      const ticker = $(cols[0]).text().trim();
      if (ticker && ticker.length <= 10) {
        tickers.push(ticker.toUpperCase());
      }
    }
  });

  if (tickers.length < 400) {
    throw new Error(`❌ Sanity check failed: only scraped ${tickers.length} tickers (expected 490+). Wikipedia table format may have changed.`);
  }

  const outputDir = path.dirname(OUTPUT_PATH);
  if (!fs.existsSync(outputDir)) {
    fs.mkdirSync(outputDir, { recursive: true });
  }

  fs.writeFileSync(OUTPUT_PATH, JSON.stringify({ tickers }, null, 2), 'utf-8');
  console.log(`✅ Wrote ${tickers.length} tickers to ${OUTPUT_PATH}`);
}

if (require.main === module) {
  generateTickers().catch((err) => {
    console.error('❌ generateTickers failed:', err);
    process.exit(1);
  });
}

export { generateTickers };
```

**Note on `__dirname` vs ts-node:** When run via `ts-node src/scripts/generateTickers.ts`, `__dirname` is `backend/src/scripts`. The `path.resolve(__dirname, '../../../frontend/src/data/tickers.json')` resolves to repo-root `frontend/src/data/tickers.json` correctly. When compiled (`tsc`) and run from `backend/dist/scripts/`, same relative path resolves identically.

### Pattern 3: CloudFront Function (URI Rewrite)

**What:** A viewer-request CloudFront Function that appends `index.html` to requests for directory-style paths so CloudFront fetches the correct object from S3.

**Why required:** With `trailingSlash: true`, Next.js emits `out/companies/index.html`. CloudFront with a private S3 origin (OAC, website hosting disabled) does NOT auto-resolve `companies/` to `companies/index.html`. Only `default_root_object = "index.html"` applies to the root `/`. All other routes return 403 from S3 (no ListBucket permission), which maps to 404 via D-09 custom error responses. Without this function, only the root page works.

**Both path styles must be handled:** The welcome page has `<a href="/companies">` (no trailing slash). CloudFront requests S3 key `companies` — which does not exist. The function must rewrite extensionless paths too.

```javascript
// Source: [ASSUMED] — standard pattern for CloudFront + S3 + trailingSlash static sites
// Deployed as aws_cloudfront_function (runtime: cloudfront-js-2.0)
function handler(event) {
  var request = event.request;
  var uri = request.uri;

  // Append index.html to directory paths (trailing slash)
  if (uri.endsWith('/')) {
    request.uri = uri + 'index.html';
  }
  // Rewrite bare extensionless paths (e.g. /companies, /company/AAPL)
  else if (!uri.includes('.')) {
    request.uri = uri + '/index.html';
  }

  return request;
}
```

**Terraform resource:**

### Pattern 4: CloudFront + OAC + S3 Bucket Policy

**Notes on AWS provider v6.x:**
- `forwarded_values` is deprecated in AWS provider v6. Use `cache_policy_id` with the AWS Managed-CachingOptimized policy ID `658327ea-f89d-4fab-a63d-7e88639e58f6`.
- `aws_s3_bucket_ownership_controls` with `BucketOwnerEnforced` is required for OAC. OAC requires ACLs to be disabled; `BucketOwnerEnforced` disables ACLs.
- `error_caching_min_ttl = 0` prevents CloudFront from caching 404 responses during testing/development.

```hcl
# Source: [CITED: raugustine.xyz/blog/private-s3-bucket-cloudfront (cross-verified with Terraform docs)]
# terraform/frontend/s3.tf

resource "aws_s3_bucket" "frontend" {
  bucket = var.bucket_name
}

resource "aws_s3_bucket_public_access_block" "frontend" {
  bucket                  = aws_s3_bucket.frontend.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

# Required for OAC — OAC requires ACLs disabled (BucketOwnerEnforced)
resource "aws_s3_bucket_ownership_controls" "frontend" {
  bucket = aws_s3_bucket.frontend.id
  rule {
    object_ownership = "BucketOwnerEnforced"
  }
}

resource "aws_s3_bucket_policy" "frontend" {
  bucket = aws_s3_bucket.frontend.id
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Sid       = "AllowCloudFrontServicePrincipal"
      Effect    = "Allow"
      Principal = { Service = "cloudfront.amazonaws.com" }
      Action    = "s3:GetObject"
      Resource  = "${aws_s3_bucket.frontend.arn}/*"
      Condition = {
        StringEquals = {
          "AWS:SourceArn" = aws_cloudfront_distribution.frontend.arn

}
```

### Anti-Patterns to Avoid

- **Calling live API in `generateStaticParams`:** The existing code calls `fetch(apiUrl + '/api/companies/')`. This fails when backend is unreachable at build time (confirmed: build fails with ECONNREFUSED). Replace entirely with `fs.readFileSync`.
- **Using bare relative paths in `fs.readFileSync`:** `readFileSync('./src/data/tickers.json')` breaks when build invocation cwd differs from expected. Always use `path.join(process.cwd(), ...)` in frontend (Next.js cwd = `frontend/`) and `path.resolve(__dirname, ...)` in backend scripts.
- **S3 static website hosting with OAC:** S3 website endpoints cannot use OAC (OAC requires REST endpoint). D-09 is correct: use `bucket_regional_domain_name` (REST endpoint) with OAC, not website endpoint.
- **Using `aws_cloudfront_origin_access_identity` (OAI):** AWS has deprecated OAI in favor of OAC. Use `aws_cloudfront_origin_access_control` + service principal bucket policy.
- **Omitting `aws_s3_bucket_ownership_controls`:** OAC requires ACLs to be disabled. Without `BucketOwnerEnforced`, the OAC setup may fail or produce unexpected access errors.
- **Using `forwarded_values` in AWS provider v6:** Provider v6 deprecates `forwarded_values`. Use `cache_policy_id` with the AWS Managed-CachingOptimized ID.
- **URI rewrite handling only trailing slashes:** The welcome page links to `/companies` (no trailing slash). Without `else if (!uri.includes('.'))`, bare extensionless paths receive a 403 from S3 → serve 404 page.
- **Omitting `error_caching_min_ttl = 0` on custom_error_response:** Without this, CloudFront caches error responses for the default 300 seconds. During development/testing this causes stale 404s after fixing routes.
- **Not validating scrape count in `generateTickers.ts`:** If Wikipedia changes their table format, silent 0-ticker output would produce a `tickers.json` with an empty array, causing `next build` to produce 0 company pages with no obvious error.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| CloudFront URI rewrite | Custom Lambda@Edge | `aws_cloudfront_function` | CloudFront Functions run at edge (sub-ms); Lambda@Edge has cold starts and is overkill for a string replace |
| S3 bucket policy JSON | Template string | `jsonencode({...})` in Terraform | Type-safe, readable, handles escaping |
| Wikipedia table parsing | Regex on raw HTML | `cheerio` (already in project) | Pattern already proven in `scrapeSP500.ts` |
| Tick existence check in Next.js | Custom middleware | `dynamicParams = false` | Built-in Next.js behavior: returns 404 for any ticker not in `generateStaticParams` return value |

**Key insight:** The URI rewrite is a pure string operation — CloudFront Functions (JavaScript at edge, no cold start) are the canonical solution. Lambda@Edge adds unnecessary complexity and cost.

## Common Pitfalls

### Pitfall 1: `trailingSlash: true` + OAC = All Subpages Return 404

**What goes wrong:** CloudFront with private S3 origin cannot auto-serve `index.html` for subdirectory requests. `default_root_object` only applies to root `/`. Every other path (`/companies/`, `/company/AAPL/`) receives a 403 from S3 (no ListBucket permission), which custom_error_response maps to 404.

**Why it happens:** S3 REST endpoint (required for OAC) does not support index documents. Only S3 static website endpoint does, but that endpoint cannot use OAC.

**How to avoid:** Add `aws_cloudfront_function` for viewer-request URI rewrite appending `index.html` to both trailing-slash and bare extensionless paths.

**Warning signs:** After deploy, `/` works, all other routes return 404.

**VERIFIED:** Confirmed by running build and observing `out/company/AAPL/index.html` output structure. `[VERIFIED: local build test + AWS documentation]`

### Pitfall 2: Bare Extensionless Paths Not Rewritten

**What goes wrong:** The CloudFront Function only rewrites trailing-slash paths. The existing welcome page contains `<a href="/companies">` (no trailing slash). This results in a 403 from S3 → serves 404 page instead of the companies list.

**Why it happens:** `trailingSlash: true` causes outbound links from Next.js components to use trailing slashes, but external links, bookmarks, and anchor-tag `href` values may omit the trailing slash.

**How to avoid:** Include `else if (!uri.includes('.')) { request.uri = uri + '/index.html'; }` in the CloudFront Function — see Pattern 3.

**Warning signs:** `/companies/` works but `/companies` (no trailing slash) returns 404.

### Pitfall 3: 404 Page Location with `trailingSlash: true`

**What goes wrong:** `trailingSlash: true` causes Next.js to generate BOTH `out/404.html` AND `out/404/index.html`. The D-09 CloudFront error configuration uses `/404.html` which is correct.

**Why it happens:** Next.js treats the 404 page as both a special static file and a routed page.

**How to avoid:** No action needed — `out/404.html` exists and contains the custom content. Use `/404.html` (not `/404/index.html`) in CloudFront `response_page_path`.

**VERIFIED:** Confirmed by local build test on Next.js 15.4.1. `[VERIFIED: local build test]`

### Pitfall 4: Build Fails When NEXT_PUBLIC_API_BASE_URL Unset

**What goes wrong:** `frontend/src/lib/api.ts` throws at module load time if `NEXT_PUBLIC_API_BASE_URL` is missing in production. During `next build`, server components importing `api.ts` will fail with "NEXT_PUBLIC_API_BASE_URL is required in production".

**Why it happens:** `frontend/src/app/companies/page.tsx` imports `CompaniesTable`, which is a client component importing hooks that import `api.ts`. During static prerendering of `/companies`, `api.ts` loads and throws.

**How to avoid:** Build command must set `NEXT_PUBLIC_API_BASE_URL`. Example: `NEXT_PUBLIC_API_BASE_URL=https://api.example.com npm run build`. This can be a placeholder URL for build — client-side fetching uses the value at runtime from the embedded JS.

**Warning signs:** Build output: `Error: NEXT_PUBLIC_API_BASE_URL is required in production` on `/companies/page`.

**VERIFIED:** Confirmed in build test run. `[VERIFIED: local build test]`

### Pitfall 5: Wikipedia Scraper Column Index Fragility

**What goes wrong:** `scrapeSP500.ts` uses `columns[0]` for ticker (first `<td>` in each row). If Wikipedia adds a new leading column (e.g., a number column) the tickers extracted would be wrong.

**Why it happens:** Positional column extraction is fragile against table structure changes.

**How to avoid:** Add a sanity check — if fewer than 400 tickers scraped, throw with a clear error. This prevents silent production of an empty or corrupt `tickers.json`.

**Warning signs:** Script succeeds but writes < 400 tickers.

### Pitfall 6: `generateTickers.ts` Path Depends on Execution Context

**What goes wrong:** If `OUTPUT_PATH` uses `process.cwd()` instead of `path.resolve(__dirname, ...)`, the output location changes depending on where `ts-node` is invoked from. Running from repo root (`ts-node backend/src/scripts/generateTickers.ts`) vs from `backend/` directory gives different absolute paths.

**Why it happens:** `process.cwd()` is the shell's working directory; `__dirname` is the file's location (stable regardless of cwd).

**How to avoid:** Use `path.resolve(__dirname, '../../../frontend/src/data/tickers.json')` in the script. Add to `backend/package.json` scripts: `"generate-tickers": "ts-node src/scripts/generateTickers.ts"` and instruct users to run via `npm run generate-tickers` from `backend/`.

### Pitfall 7: Build Time for 500 Pages

**What goes wrong:** Build may take 60-120 seconds for 500 pages (noted in STATE.md).

**Why it happens:** Next.js pre-renders each page as static HTML at build time.

**How to avoid:** No mitigation needed — this is expected behavior for 500 static pages. Document in CI pipeline expectations.

## Security Domain

This phase adds infrastructure (S3 + CloudFront) but no authentication or user data.

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | No | Public read-only site — no auth |
| V3 Session Management | No | Static site — no sessions |
| V4 Access Control | Yes (infra) | S3 bucket is private; only CloudFront OAC can access it |
| V5 Input Validation | No | No user input; static HTML only |
| V6 Cryptography | No | CloudFront handles HTTPS; no crypto in app code |

### Known Threat Patterns for Static S3 + CloudFront

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Direct S3 bucket access bypassing CloudFront | Elevation of privilege | Private bucket + OAC bucket policy restricts access to CloudFront service principal only |
| S3 bucket enumeration | Information disclosure | `aws_s3_bucket_public_access_block` blocks all public access; no ACLs |
| Stale 403 error caching | Denial of service | Set `error_caching_min_ttl = 0` on `custom_error_response` blocks |

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| OAI (`aws_cloudfront_origin_access_identity`) | OAC (`aws_cloudfront_origin_access_control`) | 2022 | OAC supports all AWS regions, SSE-KMS; OAI deprecated but not yet removed |
| `next export` CLI command | `output: 'export'` in next.config.js | Next.js 13.4 (`next export` removed in v14.0.0) | Already using correct approach |
| Lambda@Edge for URI rewrite | CloudFront Function | 2021 | Sub-millisecond execution, no cold starts, lower cost for simple rewrites |
| S3 static website hosting (public) | Private S3 + OAC | Best practice shift | Must pair with CloudFront Function for index.html resolution |
| `forwarded_values` in cache behavior | `cache_policy_id` with managed policy | AWS provider v6 | `forwarded_values` deprecated; use managed CachingOptimized policy ID |

**Deprecated/outdated:**

- `aws_cloudfront_origin_access_identity`: Deprecated by AWS. Use `aws_cloudfront_origin_access_control` instead.
- `next export` CLI command: Removed in Next.js 14. The project already uses `output: 'export'` in `next.config.ts`.
- `getStaticPaths` / `getStaticProps`: Pages Router only. Project uses App Router's `generateStaticParams`.
- `forwarded_values` in `default_cache_behavior`: Deprecated in Terraform AWS provider v6. Replace with `cache_policy_id`.
